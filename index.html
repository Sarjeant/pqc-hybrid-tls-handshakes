Hybrid post-quantum key exchange in production TLS 1.3

X25519MLKEM768 (X25519 + ML-KEM-768, FIPS 203; RFC 10024) compared with classical X25519 in real TLS 1.3 handshakes against three public endpoints, using stock OpenSSL 3.5.4 from a qBraid cloud vantage served by Cloudflare's IAD data centre (Ashburn, Virginia).

Seven sessions on 1 October and 21–23 November 2026 (UTC). Each session: 30 rounds × 3 endpoints × 2 groups, in shuffled order within each round.

Where the extra bytes go

Handshake message sizes for cloudflare.com, captured with openssl s_client -msg on 21 November 2026. The ClientHello grows by 1,176 bytes: the key share adds the 1,184 bytes RFC 10024 specifies, and OpenSSL drops an 8-byte ec_point_formats extension when only the hybrid group is offered. The ServerHello grows by exactly the 1,088-byte ML-KEM-768 ciphertext.

ClientHello extensions (bytes on the wire)

With the 5-byte record header the hybrid ClientHello is 1,416 bytes (1,427 for pq.cloudflareresearch.com), below the 1,460-byte maximum segment size of a standard Ethernet path, so it still travels in one TCP segment.

What this does and does not show

  • Interoperability: every one of the 1,260 handshakes completed, and all 630 hybrid attempts negotiated X25519MLKEM768. Only one group was offered per attempt, so no silent fallback was possible.
  • Timing: no endpoint shows a resolved difference. The intervals are descriptive and were not designed as an equivalence test.
  • Scope: one cloud vantage on short, low-latency paths, three anycast endpoints served from one data centre. Results do not extend to high-latency, lossy, mobile or constrained networks, or to post-quantum certificates and signatures.
  • Measure: “startup-adjusted handshake time” is the duration of the s_client process minus OpenSSL start-up time. It includes name resolution, the TCP handshake and process exit, so it is an end-to-end proxy, not cryptographic computation time.
